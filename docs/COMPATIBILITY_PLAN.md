## Purpose and constraints

Deliver the same floating F2L companion on the user's Mac and a teammate's Windows computer. Both platforms belong to the planned release, with equivalent character states, separate temporary input and speech-bubble output, pointing, pause and interruption behavior. Use menu-bar access on Mac and system-tray access on Windows. Do not add a persistent sidebar or main chat window. Keep future changes and builds local; do not commit, push, publish, or upload them as part of this plan.

The original implementation was generated by Claude. There is no separate active Claude session coordinating this work.

The current Mac app and the earlier local fixes have not been compiled or tested on macOS during this review. There are 33 test functions in the current working copy, but their presence is not a passing test result. See [LOCAL_REVIEW.md](LOCAL_REVIEW.md) for the earlier changes and outstanding checks.

## Recommended approach

Keep the Swift Mac app and add a native C# Windows app. For the competition, this is the proposed lowest-risk route because it preserves the existing Mac implementation and permits an incremental Windows prototype.

This produces two native implementations with shared specifications, prompts and test fixtures, not one executable codebase. The tradeoff is maintaining equivalent behavior in two languages.

A shared Electron interface remains an alternative for later discussion. It would still require platform-specific integrations for reliable accessibility-based pointing and would replace more of the existing app. Docker does not supply the macOS frameworks or desktop environment needed to run this app on Windows.

| Function | Existing Mac app | Proposed Windows app |
|---|---|---|
| Interface and screen guidance | Swift/SwiftUI and AppKit | C# with WPF; screenshot-based outline when the model returns a target |
| Read controls | macOS Accessibility | Windows UI Automation |
| Capture target window | ScreenCaptureKit | Foreground app client-window capture with Win32 GDI in the Windows preview |
| Speech recognition | Apple speech recognition | Windows speech adapter, validated on the actual PC |
| Spoken replies | ElevenLabs and Apple fallback | ElevenLabs and Windows fallback |
| API keys | Keychain | Windows Credential Manager |
| Coaching behavior | Existing Swift logic | C# implementation with matching prompts, tools and behavior tests |

Windows runtime: .NET 10 with WPF. WPF only runs on Windows; the Mac app stays in Swift. The Windows project builds with zero warnings and errors and starts locally. When sharing is enabled, it temporarily hides F2L, snapshots the foreground app window and sends that image only with an explicit question; it does not continuously monitor or save screenshots. A model-returned target can draw a click-through highlight around part of that screenshot. This is a visual estimate, not a Windows UI Automation control match. Task verification is not implemented. The configured key previously received HTTP 401, so an actual coach reply and live target highlight remain unverified. A successful launch does not establish full cross-platform parity.

## Remaining work for a cross-platform release

### 1. Establish a trustworthy baseline

- Inspect the current working tree and preserve all existing uncommitted changes. Re-read this plan and LOCAL_REVIEW.md; do not assume the repository is unchanged since planning.
- On the Mac, build F2L and run the current Swift tests. Establish the matching Windows pointing prototype during the same foundation work package.
- Reproduce pause, interruption, capture and pointing scenarios from LOCAL_REVIEW.md.
- Record actual results and repair failures before treating the Mac implementation as the reference.

**Checkpoint:** a verified Mac baseline, with unresolved failures explicitly recorded. If the Mac is unavailable, report native verification as pending rather than claiming success.

### 2. Prove Windows pointing before porting the whole app

Build a small C# prototype that identifies the foreground browser window, reads its controls and draws a circle around a selected control. Begin with a predictable local test page, then test ChatGPT in Chrome and Edge.

Verify that the circle:

- Lands on the correct control.
- Lets clicks pass through and does not steal keyboard focus.
- Follows window movement and scrolling.
- Works across monitors, including mixed display scaling and negative desktop coordinates.
- Disappears when the target becomes invalid.

Run accessibility reads away from the interface thread, bound traversal work, and handle unavailable or unresponsive controls. Use supported Windows interop APIs or a maintained, verified wrapper.

**Checkpoint:** accurate pointing on the teammate's actual Windows PC before building the full interface. Investigate browser accessibility coverage if controls are missing; do not silently substitute unverified screenshot guesses.

### 3. Define shared behavior

Keep the existing Mac directory layout. Add a separate Windows project and shared JSON specifications and test fixtures.

- Share the coaching prompt, tool definitions, example screen contexts and expected outcomes.
- Port core logic into a C# library without Windows interface dependencies.
- Standardize control roles, coordinate units, screenshot dimensions and identifier scope.
- Associate every pointer with a turn, a specific window and a screen snapshot.
- Distinguish exact accessibility-based pointers from approximate screenshot-based regions.

**Checkpoint:** equivalent tests on both implementations cover valid pointers, invented IDs, absent screenshots, streamed replies, interruptions and coordinate conversion. Shared fixtures prevent behavior from drifting between languages.

### 4. Build the Windows coaching flow in stages

The Windows preview now supports typed questions, active-app screenshots, an AI reply, spoken output, and a screenshot-based target outline. It also has tap-to-start/stop dictation with an editable transcript. This is an implementation checkpoint; the live provider response and target placement still need verification on a valid key and real app screens.

Next validate recognition accuracy, interruptions, focus restoration, settings, and secure key storage on the target Windows PC, then align the Mac conversation. Preserve the product rule: F2L points; the learner clicks. Do not add automatic clicking or typing.

Check installed Windows speech recognizers and test accuracy and availability on the actual PC. If recognition is unavailable or inadequate, evaluate a local speech engine before choosing an additional cloud provider. Do not silently introduce a new service, account requirement or audio data transfer.

Keep proactive nudges and background summaries disabled in the initial Windows milestone. Add them once the basic conversation is reliable.

**Checkpoint:** a complete question-to-voice-and-circle interaction, with cancellation and usable error handling.

### 5. Debug known issues on both platforms

| Issue | Required behavior |
|---|---|
| Switching tabs or windows within one browser | Invalidate old targets using window identity and screen changes, not process ID alone |
| Stale background summary | Refresh or expire on relevant content changes even if the title is unchanged |
| Deleting text resembles sending a message | Treat an empty field as ambiguous without independent submission evidence |
| Pause followed immediately by Resume | Discard results from the earlier screen session |
| Password focus cannot be determined | Skip capture instead of assuming it is safe |
| Control disappears during a reply | Reject the pointer and obtain fresh context |
| Network or audio device failure | Recover without frozen controls, overlapping speech or repeated sentences |
| Display scaling and coordinate mismatch | Convert explicitly between capture pixels, desktop coordinates and overlay layout units |

Use simulated delayed responses and failures for repeatable tests. Include malformed stream fragments, missing keys, interrupted playback, permission denial and disappearing windows. Log timings and error categories without storing screenshots, transcripts or API keys by default.

Cancellation cannot recall a capture or request already handed to the OS or a vendor. Test that no additional stale work is initiated or applied after invalidation, and do not make stronger privacy claims than the implementation supports.

### 6. Validate and package locally

Initial proposed support: macOS 15+ on Apple Silicon and Windows 11 x64, English, with Chrome as the first demo browser. Expand coverage after the baseline passes.

Run the same two demonstrations on both computers:

1. A blank ChatGPT page: "How do I start?"
2. An unfamiliar control: "What's this button?"

Acceptance criteria:

- All pause and stale-target regression tests pass.
- The learner can interrupt speech and immediately ask another question.
- At least 15 labeled screen cases are evaluated against the repository's proposed 80% pointing target.
- Measure time from releasing push-to-talk to first audible response. Pursue the existing under-2.5-second target and report actual results, not an assumed guarantee.
- The local Mac bundle and Windows package launch on the respective teammate's computer; both expose the same floating-companion behavior without requiring a main chat window.
- The temporary composer takes focus only when invoked and restores the valid teaching target safely on both operating systems. Character and bubble do not cover registered task targets; collapse and relocate fallbacks work.

Future deliverables: local builds, test results, setup instructions and an explicit list of remaining limitations. Do not claim full compatibility merely because the projects compile.

## Open decisions for further planning

- Confirm whether maintaining two native implementations is acceptable beyond the competition.
- Confirm the Windows teammate's OS version, CPU architecture, display setup and microphone.
- Decide the Windows speech engine after testing the actual machine.
- Confirm the competition deadline and available contributors. Windows support is required alongside macOS; sequence implementation without silently demoting it to a later product release.
- Decide when the Mac is available for native validation.

The first implementation milestone, if later requested, is the verified Mac baseline plus a Windows pointing prototype. Do not start the full port before those checkpoints are assessed.
